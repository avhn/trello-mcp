Trello MCP tools

Find boards, manage cards, edit checklists and handle attachments through 48 Model Context Protocol tools.

With credentials configured, all 48 tools are available by default. Read-only mode hides 29 mutation/transfer tools, leaving 19 reads and local-selection tools eligible. Without credentials, only server_health is registered with a setup hint.

  • Comments

  • Board members

Use TRELLO_TOOLS to select comma-separated tool names or prefix groups. Selectors form a union, so card includes both card-member tools. Unknown selectors fail startup; read-only filtering still applies to explicitly selected writes. Include server or server_health for diagnostics.

Common parameters and response behavior

Selection and ownership

boardId is described per tool: collection tools default to the active board, board_use requires it, and object-scoped tools take it only as an optional expected owning-board constraint, never authorization. card_find with mine: true finds account-wide assigned cards and cannot be combined with boardId or listId. board_create requires an explicit or active workspace. Comment mutations require cardId and commentId; item mutations require checklistId and itemId.

Detail and pagination

board_get, card_find and card_get support detail: "summary" (default) or "full". card_find summary returns ids, ownership, labels, members, dates, status and a description preview of at most 200 characters, with no url; full adds url, and card_get keeps url at both levels. Filters, authorization, ids and cursors are identical in both modes. card_get also supports view: "markdown" and bounded extraFields. Comments are fetched separately.

Collections return {"items":[...],"next":"cursor"}, omitting empty cursors. Cards default to 100 results (maximum 1000), comments to 20 (maximum 100), and activity/history to 20 (maximum 1000).

Argument errors identify unknown or duplicate keys and their object location. Unknown keys list allowed keys; type errors name the field and expected type.

Activity pages use the last action id as before and accept since; both take an action id or an RFC 3339 date. board_activity and card_history accept filter, default all: either all alone or comma-separated action identifiers such as commentCard, createCard or updateCard (letters, digits and underscores, starting with a letter). The grammar is open-ended and applied upstream before paging. A full page advertises a possible next page, which can be empty.

Activity, history and comments share a flat projection: id, type, date, by, then only the relevant fields. Card and list names appear when first seen in a page and whenever they change; an omitted name means the last name for that id earlier in the same page, and each new page starts fresh.

The card_find before cursor is a card id from the same filtered snapshot, never a date; dates and malformed ids are rejected before any request; a valid id absent from the freshly fetched filtered snapshot is rejected. Missing or changed cursors fail rather than restart, and snapshots are not stable across calls.

Mutations and typed values

Most writes return {id,name?,url?} or {ok:true}. Card creation can also include checklist progress and an error. Batch creation preflights arguments and referenced ids, then returns zero-based per-item results. It is not transactional: later failures do not roll back earlier cards or checklists, and batch processing continues after a per-card failure.

Create a card with an ordered checklist

card_create and each card in card_create_batch accept checklist with an optional name (default Checklist) and required items: 1-100 nonblank strings, each at most 4096 bytes, created in order.

{"listId":"l1","name":"Sound test","checklist":{"items":["SND01","SND02"]}}

Success adds checklist: {id,name,items:N}. A checklist failure keeps the card id, the checklist id if confirmed, the confirmed item count and an error naming the failed step; do not repeat card creation, inspect with checklist_get and checklist_item_find first.

pos accepts top, bottom or a positive number. Dates use RFC 3339. Empty due or start clears dates, and optional booleans preserve explicit false. Update tools require at least one update field.

Use customfield_find to discover field types and dropdown option ids. customfield_set requires exactly one of a typed scalar value or dropdown idValue. Clear a scalar with value: "" or a dropdown with idValue: "".

Mutation verification and partial results

Clearing due, start or a label color with an empty string is sent as query parameters, because an HTTP JSON null is ignored upstream; checklist item due and memberId do too. The response is checked first and requested values that come back are compared with no extra request. A GET happens only for fields the response omits. No retry follows an ambiguous transport failure, invalid success response or verification mismatch; HTTP 429 allows at most three.

When the object is confirmed but a requested field is not, the result is {id, error, unconfirmed} and sets MCP isError. The mutation may have been applied, so inspect the object before repeating anything; a created card or item is never recreated to repair a partial result. In live checks Trello ignored checklist item due and memberId while still answering with a populated item, so those requests surface as partial results.

checklist_get matches an exact name. On a miss it returns an error with the searched name, up to 20 available {id,name} choices, total and truncated, and no items.

Attachment and policy checks

attachment_upload requires exactly one confined local path or standard base64; base64 also requires fileName. Both upload and download have a 10 MiB cap. Local path uploads and downloads fail closed on Windows.

server_health accepts basic, detailed, metadata, performance or policy as detail. Use {"detail":"policy"} to inspect restrictions before treating a refusal as a token problem.
