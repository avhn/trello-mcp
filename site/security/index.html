Access boundaries and local files

Security and access policy

Token permissions are the ceiling. trello-mcp adds workspace restrictions, ownership checks, optional read-only mode and confined attachment transfers.

  • Read-only
  • Policy discovery
  • Credentials
  • File transfers

Workspace allowlist and object ownership

TRELLO_ALLOWED_WORKSPACES accepts comma-separated workspace ids or canonical names, not display names. Unset means unrestricted within your token's permissions. This is additional server policy, not a replacement for token permissions.

  • Every scoped read and write resolves the actual owning board. A supplied boardId is a constraint, never authorization.
  • Moves and copies check source and destination. Comments, checklist items, attachments, labels, custom fields and member references are verified against their actual parents before mutation.
  • Unverifiable ownership fails closed. Ownership grants are not cached across calls, so moved boards are rechecked.
  • Policy denials include configured selectors and only caller-supplied object ids, not resolved denied board or workspace ids or names.

Trello has no atomic authorization-and-mutation API. Local ownership checks cannot prevent concurrent upstream moves between verification and mutation.

Writes are enabled by default; read-only is opt-in

trello-mcp auth --read-only

Alternatively, set TRELLO_READ_ONLY=1 in the server's environment. It hides all 29 mutation/transfer tools, including downloads that write local files. The 19 reads and local-selection tools remain eligible, subject to your tool profile.

A saved scope=read token implies read-only mode even with TRELLO_READ_ONLY=0. workspace_use and board_use still change local defaults. Read-only server policy does not replace a suitably scoped Trello token.

TRELLO_TOOLS selects comma-separated tool names or prefix groups. Selectors form a union; unknown selectors fail startup. Read-only filtering still applies to explicitly selected write tools. Include server or server_health in custom profiles to retain diagnostics.

Discover the effective access policy

MCP initialization instructions summarize configured workspace restrictions, read-only mode and effective file-transfer availability without including credentials or saved active ids.

If a tool is hidden or an operation is refused, call server_health with:

{"detail":"policy"}

Policy health reports restricted, allowedWorkspaces, readOnly, credentialScope when loaded from file, toolProfile, enabledToolCount, hiddenWriteTools, plus uploads and downloads with enabled and dir.

  • Allowed workspace entries contain the configured selector and resolved id and canonical name when available. Only allowed workspace names are returned.
  • One cached, best-effort workspace lookup resolves selectors. Failure leaves them unresolved without failing health. This diagnostic cache never grants authorization.
  • Transfer availability accounts for profile selection, read-only mode and platform support. Uploads here means local path uploads, not base64.
  • Directory paths describe configuration, not a filesystem readiness check. Health is not an upstream readiness check.

Server policy is not a broken token

Policy denials explicitly say they are server policy, not a token/permission error, and include corrective guidance. Upstream failures use trello API: HTTP <status>; 401/403 identify a token/permission issue. Do not change credentials to fix server policy.

With no credentials, only server_health is registered, regardless of the selected profile. Every health mode includes the hint to run trello-mcp auth to save ~/.secrets/.trello-mcp.secret or set both environment credentials. Invalid-token HTTP 401 errors include the setup hint too.

Saved credentials and file permissions

The default is ~/.secrets/.trello-mcp.secret on all platforms, using os.UserHomeDir(); on Windows it is %USERPROFILE%\.secrets\.trello-mcp.secret. MCP client configs need only the full binary path, without credential env blocks.

Paths and unquoted KEY=VALUE rules follow avhn/secret, "Let coding agents use your credentials without reading them". The bare name trello-mcp resolves to this dedicated file in secret, so secret show trello-mcp lists masked names and secret exec -f trello-mcp ... can launch a configured consumer. Values follow secret stash rules. Using avhn/secret is optional; trello-mcp reads the files itself.

TRELLO_API_KEY=your-api-key
TRELLO_TOKEN=your-token
TRELLO_TOKEN_SCOPE=read,write

Scope is optional: absent means unknown and is treated as writable; read forces read-only even with TRELLO_READ_ONLY=0. Values reject empty strings, NUL, CR, embedded newlines, boundary whitespace and surrounding quote pairs. A final LF is allowed. Saves rewrite only these three keys and preserve all unrelated lines, comments and their order byte-for-byte.

  • trello-mcp auth creates missing parent directories as 0700 and the file as 0600 on Unix, or protected owner-only DACLs on Windows. It never changes an existing folder's permissions.
  • Existing Unix directories must belong to the current user and not be group/world writable (0755 is allowed). Files must be current-user-owned and not group/world accessible. Windows verifies ownership and protected owner-only DACLs on both.
  • Symlinked files or parent paths and nonregular files are refused. Writes use a private temporary file in the same directory, fsync and atomic rename in a pinned directory.
  • The file remains plaintext. Protect backups. The hidden token prompt does not make the authorization URL safe to share: it contains the API key.

Precedence, shared fallback and auth commands

Precedence is environment TRELLO_API_KEY + TRELLO_TOKEN > absolute TRELLO_MCP_CREDENTIALS file > ~/.secrets/.trello-mcp.secret > ~/.secrets.env. Both environment values are required together; a partial pair is an error. Missing or credential-free files fall through; malformed or unsafe earlier files fail closed. Sources are never merged.

~/.secrets.env is secret's shared top-level store. Only the three Trello keys are interpreted there, and both key and token must be present in that same file. Unrelated keys and values are ignored and never logged. The shared file has the same owner, no-symlink and private-file checks; the home directory does not need an owner-only Windows DACL. An unsafe shared file is bypassed if an earlier source exists; otherwise a clear error is returned. Auth never writes to or logs out of this shared store.

trello-mcp auth --file /absolute/path/account.secret
trello-mcp auth status --file /absolute/path/account.secret
trello-mcp auth logout --file /absolute/path/account.secret

--file overrides the path for that command only. Set TRELLO_MCP_CREDENTIALS in the MCP server environment to use a custom file in clients; the complete environment credential pair still overrides it.

auth status validates identity and actual granted scope with Trello and prints one fact per line, never credentials: Credential source: env (TRELLO_API_KEY, TRELLO_TOKEN) or Credential source: file <path>, followed by Connected as <username>, scope <granted scope>. Shared fallback reports Credential source: file ~/.secrets.env (shared store). With none found it explains that clients may supply their own configuration and suggests auth. Failed validation says to check the token and read permission.

auth logout removes only the three Trello keys and deletes the file only if nothing remains. Unrelated lines and comments survive. It does not revoke the token, unset environment credentials or alter the shared store; those sources may still authenticate. Restart clients after changes.

Manual setup without the browser flow

If you already have credentials, create a missing directory with mkdir -m 700 ~/.secrets on Unix, start a private editor after umask 077, and write the three lines above with your own values and actual scope. Run chmod 600 ~/.secrets/.trello-mcp.secret. Do not automatically chmod an existing shared folder. With secret installed, secret stash trello-mcp TRELLO_API_KEY and corresponding token/scope commands prompt privately; never put values in arguments or chat. Windows manual setup requires current-user ownership and protected owner-only DACLs in Properties > Security for both folder and file. Run trello-mcp auth status afterward.

Permission errors and safe fixes

The CLI prefixes errors with trello-mcp auth:. Resolver errors may also identify the file path. Exact storage messages include:

  • credentials directory is group/world writable; remove group/world write permissions (chmod go-w) or choose a private directory with TRELLO_MCP_CREDENTIALS
  • credentials file is group/world accessible; chmod 600 the credentials file or rerun trello-mcp auth
  • credentials must be owned by the current user; rerun trello-mcp auth as that user
  • credentials parent must be a directory, not a symlink; choose a real directory with TRELLO_MCP_CREDENTIALS
  • credentials file must be a regular file, not a symlink
  • credentials require a protected owner-only Windows DACL and ownership by the current user; remove access for other users in Properties > Security on the credentials directory and .trello-mcp.secret, then rerun trello-mcp auth

Repair only a path you own and intend to keep private, or choose a new private directory with TRELLO_MCP_CREDENTIALS. Replace symlinks with real paths and run as the correct owner, rather than bypassing checks.

Short troubleshooting checklist

  • No credentials found or only server_health: run trello-mcp auth, check overrides, then restart your client; its own environment may differ from your shell.
  • Permission refused: apply the exact corrective message above or choose a new private path; auth never chmods existing folders.
  • 401 token rejected: check token expiry, revocation and matching API key, then reconnect. 403 may mean insufficient permission.
  • Wrong workspace denial: inspect server_health with {"detail":"policy"} and correct the allowlist or object selection. This is server policy, not necessarily a broken token.

Attachment uploads and downloads

Local path uploads are disabled by default

Set TRELLO_UPLOAD_DIR to an absolute, dedicated staging directory containing only files intended for upload. Do not choose your home directory or a credential directory.

Only regular files inside that root may be uploaded. Paths escaping the root are refused; the root and every component below it must not be symlinks. Unix uses a pinned root descriptor and no-symlink component traversal. Dot-files and dot-directories inside the root are allowed, so the root's contents matter.

Base64 uploads do not need TRELLO_UPLOAD_DIR because the caller already supplies the bytes. They require fileName. Uploads accept exactly one of path or base64, and are capped at 10 MiB.

Downloads use private storage

TRELLO_DOWNLOAD_DIR defaults to os.TempDir()/trello-mcp. Missing directories are created as 0700; existing ones must be private, owned by the current user and not symlinks.

Downloads verify card ownership and attachment membership, use the attachment's fileName and OAuth headers without query credentials, and refuse redirects. Files are created exclusively as 0600 under a pinned directory root. Existing files and symlinks are never overwritten; failed or oversized transfers are removed.

Downloads are capped at 10 MiB and return only path, size and mimeType, never inline file bodies. attachment_find returns metadata and link URLs, omitting OAuth-protected uploaded-file URLs.

Windows fails closed for local file transfers

Ownership and path verification for local uploads and downloads currently require Unix, including Linux and macOS. Other platforms refuse those operations. Base64 uploads and URL attachments remain available when writes are enabled. URL attachments are passed to Trello; this process does not fetch arbitrary attachment URLs locally.

Read-only mode hides all attachment transfers, including downloads, but keeps metadata discovery available.

Defensive HTTP and response handling

Requests have deadlines, redirects are refused, credentials are scrubbed from errors and upstream error bodies are not returned. JSON API responses are capped at 8 MiB. Tool results use compact text-only JSON, without output schemas, duplicate structured content or inline attachment bodies.

Rate limits and retries are bounded per process. Other clients sharing your credentials still consume the same upstream quota. After an ambiguous write failure, do not blindly repeat the operation: it may already have succeeded.
